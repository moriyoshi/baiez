# Validation and benchmarks

## Workflow attestation

`scripts/attest_workflow.py` loads the real fixture generated by
`scripts/measure_lightgbm.py` into a yesnodb bundle, dumps the model, and
checks CLI and Python indexed predictions against LightGBM's saved raw scores.
The routine gate uses a hash-pinned 1,024-row slice of that fixture under
`tests/fixtures/lightgbm_regression_1024/`; the full 100,000-row report below
remains the broader attestation and measurement reference.
It also checks separate model/index loading, a three-iteration leaf-output
window, and rejection of an unknown row ID. With NumPy available:

```console
cargo build --offline --features python --bin baiez --lib
python3 scripts/attest_workflow.py /tmp/baiez-lightgbm-measure
```

On the available 100,000-row, eight-feature, 16-tree regression fixture,
8,152 feature values are missing and 8,985 are zero. JSON model dumping
matched the source byte for byte. Across cohorts of 1, 64, 1,024, 8,192,
shuffled scattered 8,192, and all 100,000 rows, both CLI and Python maximum
absolute error against saved LightGBM raw scores was at most `4.44e-16`.
The leaf window and unknown-row checks passed. This attestation uses saved
LightGBM scores; a live LightGBM library was unavailable for native-text
import or ordinary `Booster.predict(X)` checks in this run.
The complete machine-readable result, including SHA-256 hashes of the fixture
and tested binaries, is in `reports/gbm_workflow.json`.

## Measurement

`scripts/measure_lightgbm.py` trains a real LightGBM 4.7.0 regression model on
100,000 rows with eight numeric features and exports the model, rows, and native
raw scores. `examples/measure_real.rs` builds the corresponding packed index,
checkpoints it, verifies scores against LightGBM, and times the scorer. The
model has 16 trees, 104 distinct split predicates, and 5,851,779 packed
memberships. Every reported score differs from LightGBM by at most `4.44e-16`.

With `lightgbm` and `numpy` installed in the active Python environment:

```console
python3 scripts/measure_lightgbm.py /tmp/baiez-lightgbm-measure
cargo build --release --example measure_real
taskset -c 19 target/release/examples/measure_real /tmp/baiez-lightgbm-measure
```

Choose a CPU allowed by your machine's affinity mask in the last command.

The table uses a pinned AArch64 Cortex-X925 core. LightGBM is called through
its C API with preallocated input and output buffers and one prediction thread.
`Prepared flat` is the median of seven repeated `predict_into` samples with a
reused output buffer. Scattered cohorts are tested in ascending row order and
with a fixed permutation that repeatedly crosses chunk boundaries.
Model loading, index construction, checkpointing, snapshot preparation, and
cohort selection are outside prediction timings.

| Cohort | LightGBM C API | Prepared flat |
| --- | ---: | ---: |
| 1 contiguous row | 6.31 us | 0.29 us |
| 64 contiguous rows | 12.91 us | 6.89 us |
| 1,024 contiguous rows | 119.39 us | 108.88 us |
| 8,192 contiguous rows | 1.04 ms | 1.09 ms |
| 8,192 scattered rows | 1.03 ms | 1.11 ms |
| 8,192 shuffled scattered rows | 1.04 ms | 1.19 ms |
| All 100,000 rows | 13.37 ms | 5.24 ms |

The Python `ctypes` call adds fixed overhead to the C API measurement,
especially for one row. Direct container access reduced the ascending
8,192-row scattered call from 1.87 ms to 1.11 ms. Snapshot preparation took
403 us for this model. Index construction took 0.15 s and checkpointing
0.11 s. The checkpointed
database occupied 1,839,104 allocated disk bytes, excluding features and the
model. All scores matched LightGBM within `4.44e-16` absolute error. The
synthetic probe in `examples/measure.rs` can vary row and tree counts.

### Python binding and CLI workflow

`scripts/measure_workflow.py` measures the release Python binding and the new
bundle CLI on the same fixture. Repeated runs pinned the process to CPU 19
on the AArch64 Cortex-X925 machine. Hot Python calls reuse one prepared index;
CLI calls launch a process, open and prepare the bundle, read an ID JSON file,
and write prediction JSON. Each run reports medians of seven timed samples;
the table shows the observed range of those medians.

```console
cargo build --release --offline --features python --lib --bin baiez
taskset -c 19 python3 scripts/measure_workflow.py /tmp/baiez-lightgbm-measure
```

| Cohort | Python `predict_ids()` | CLI process |
| --- | ---: | ---: |
| 1 row | 1.3 us | 32-38 ms |
| 64 contiguous rows | 6.5-7.1 us | — |
| 1,024 contiguous rows | 84-96 us | — |
| 8,192 contiguous rows | 1.06-1.07 ms | 36-40 ms |
| 8,192 shuffled scattered rows | 1.06-1.12 ms | 36-38 ms |
| All 100,000 rows | 5.3-5.5 ms | 89-100 ms |

The direct extension call, given pre-encoded row IDs, took about 0.4 us for
one row and 5.4 ms for all rows. The Python wrapper adds about 0.9 us to a
one-row call and less than 0.1 ms to the full batch. Combined model/index
loading through the CLI took 286-305 ms after the row JSON file had been
created. Opening and preparing the Python bundle took 31-34 ms. The yesnodb
database
occupied 1,900,544 allocated bytes, including model metadata. The full
machine-readable results and timing ranges are in
`reports/workflow_performance.json`.

## Arrow Flight over loopback TCP

`examples/measure_flight.rs` starts an Apache Arrow Flight `DoExchange`
server with a prepared index, then sends one Arrow `UInt64` row-ID batch per
request and receives a `Float64` score batch. It uses a real TCP socket on
`127.0.0.1` and reuses the Flight connection. The server and client run in one
process. Model loading, index construction, connection setup, and Arrow input
batch construction are outside the timer. Request encoding, the RPC, server
decoding and inference, response encoding, and client decoding are inside it.
The server socket has TCP no-delay enabled.

```console
cargo build --release --offline --features flight-benchmark --example measure_flight
taskset -c 19 target/release/examples/measure_flight /tmp/baiez-lightgbm-measure
```

Repeated runs pinned to the same Cortex-X925 core gave:

| Cohort | Local `predict_into` | Flight round trip |
| --- | ---: | ---: |
| 1 row | 0.29-0.30 us | 37-41 us |
| 64 contiguous rows | 6.5-6.8 us | 48-50 us |
| 1,024 contiguous rows | 105-110 us | 153-159 us |
| 8,192 contiguous rows | 1.06-1.12 ms | 1.17-1.21 ms |
| 8,192 scattered rows | 1.08-1.12 ms | 1.17-1.22 ms |
| 8,192 shuffled scattered rows | 1.17-1.22 ms | 1.28-1.33 ms |
| All 100,000 rows | 5.14-5.36 ms | 6.05-6.23 ms |

The full request sends about 0.8 MB of row IDs and returns about 0.8 MB of
scores. The round trip adds roughly 0.9 ms at that size; for a single row,
Flight overhead dominates inference. A second machine would add network
latency and bandwidth limits that this loopback test does not measure. Every
Flight response matched the LightGBM fixture within `4.44e-16` absolute error.
